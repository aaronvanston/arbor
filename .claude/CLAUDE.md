# Working on Arbor

Kept by hand, separately from `AGENTS.md` at the repo root. The two cover the same
ground in their own words. Never generate one from the other, merge them, or add an
`@` import between them. When a rule changes, edit both.

## The project

Arbor is a Tauri 2 desktop app for macOS that wraps CLIProxyAPI, called "the core" in
the code: a local proxy that shares a person's own Codex, Claude, xAI and other
subscription accounts between the agents on their own machines. Arbor starts the core,
edits its config, handles sign-in, tracks account limits, and records usage, machines,
agent sessions and each machine's agent setup. It's a fork of EasyCLIProxyAPI, MIT
licensed; `THIRD_PARTY_NOTICES.md` (`bun run notices`) has what it includes.

- Webview: React 19, TypeScript, Tailwind CSS v4, Base UI (`@base-ui/react`),
  Hugeicons (`src/components/ui/icons.tsx`).
- Native side: Rust in `src-tauri/`, with SQLite through `rusqlite`.
- Tooling: Bun installs packages and runs the tests.
- The bundle id is `onl.arbor.app`. The real app keeps its config, credentials and
  usage history in `~/Library/Application Support/onl.arbor.app`; don't go there, nor to
  `com.cpa.gui` beside it, the old id's folder, which `app_identity.rs` moves across
  on the first launch and leaves as a link.
  The session archive is live data as well: its index sits in `session-archive/` in
  that folder and its store on the drive chosen in Settings › Session Archive. Don't open
  or change either.

## Running things

```sh
bun install                 # use --frozen-lockfile when dependencies aren't changing
bun run verify              # all the TypeScript checks listed below
bun run verify:rust         # Rust tests
bun run build               # tsc + vite build into dist/ (compiles the Tailwind CSS)
bun run bindings            # rewrites src/native/types.ts from the Rust types
bun test tests/x.test.ts    # a single suite
```

`src-tauri/src/usage/bench.rs` times each page's reads on a usage.db of a million
requests. It's `#[ignore]`d and only means something in release, where SQLite is
compiled optimized: `cd src-tauri && cargo test --release usage::bench -- --ignored
--nocapture`, with `ARBOR_BENCH_DIR=<dir>` to reuse the filled database next time.

What each `package.json` script runs:

| Script | Command |
| --- | --- |
| `typecheck` | `tsc --noEmit` over `src/`. Beyond `strict`, `tsconfig.json` turns on `noUncheckedIndexedAccess`, `noImplicitReturns`, `noFallthroughCasesInSwitch` and `noImplicitOverride`. |
| `typecheck:tests` | `tsc -p tsconfig.test.json --noEmit`: `src/` and `tests/` together, same flags, plus Bun's types. |
| `lint` | `oxlint --disable-nested-config` with `.oxlintrc.json`. `.gitignore` already hides `.claude/worktrees` from oxlint; the flag makes sure a worktree's own copy of the config can never apply even if it didn't. |
| `knip` | `knip` with `knip.json`: unused files, exports and dependencies. |
| `test` | `bun test`. |
| `verify` | typecheck, typecheck:tests, lint, knip, test, in that order; the first failure stops it. |
| `verify:rust` | `cd src-tauri && cargo test`. Includes the bindings test, which fails when `src/native/types.ts` is out of date. |
| `bindings` | That test with `ARBOR_WRITE_BINDINGS=1`, which rewrites the file. |
| `build` | `tsc && vite build`, into the gitignored `dist/`. `verify` doesn't run it, and it's the only gate that compiles `src/styles.css`. |

Before it downloads, versions or builds anything, `scripts/publish-local-update.sh`
runs `bun run verify`, then `bun run verify:rust`, and gives up if either fails.
Setting `ARBOR_SKIP_VERIFY=1` skips both and prints a warning. Save that for an
urgent build, not for getting past a failure nobody has read.

Finish with `bun run verify` and `bun run build` (and `bun run verify:rust` after
Rust changes). The release script only reaches `bun run build` through
`bun tauri build`, after it has already bumped the version, so a build failure has to
be caught here. Never start `bun tauri dev`, which launches the real app, or
`bun tauri build`, which only the release script runs.

## Seeing the UI

Serve the app with the mock:

```sh
bunx vite --host 127.0.0.1 --port 1420 --strictPort
```

and open http://127.0.0.1:1420. The flags matter: bare `vite` binds only `::1`, and
`bun run dev` binds every interface.

`src/main.tsx` installs `src/dev/mockTauri.ts` when it's a Vite dev build and there's
no Tauri shell. The mock answers every command in the list, including the core's
management API behind `management_request`, through `mockCommands`
(`src/dev/mock/answers.ts`). Each domain's answers are a map typed against its command
list, so the compiler rejects a missing, extra or wrongly shaped answer. Each domain's
answers and fixtures sit in `src/dev/mock/` in a file named for it (`app.ts`, `core.ts`,
`usage.ts`, `machines.ts`, `setup.ts`, `archive.ts`), built from the generated types;
`scenario.ts` holds what they share.

Scenarios come from the query string, like `?health=down` or `?core=stopped`. They're
listed in the doc comment at the top of `src/dev/mockTauri.ts`, with a few more noted
next to their `params.get(` calls; check there instead of copying the list. Every new
UI state (a failure, an empty list, a warning) should get its own flag, documented in
that comment. A new Tauri command needs an answer in its domain's map, and one the
webview no longer calls loses its answer with its list entry.

## How code is written here

- Follow the style of the file you're in; keep diffs to the task.
- No literal UI text in components. Add a key to `src/i18n/locales/en.ts` and read it
  with `const { t } = useI18n()`, `t('some.key', { count })` filling `{count}`. That
  goes for `aria-label`, `title` and `placeholder` too; `tests/uiLocalization.test.ts`
  catches misses. Services that produce text take a `t` or return a `MessageKey`.
- Copy: plain words, short, sentence case. Tell the user what happened and what they
  can do.
- Write US English everywhere: UI text, messages, comments, docs, names, commits and
  release notes (color, behavior, canceled, gray, organize). `tests/i18n.test.ts`
  checks the UI text and `release-notes.mjs` refuses British spelling, both from the
  list in `scripts/us-spelling.mjs`. Other programs' names keep their own spelling
  (tokio's `is_cancelled`, `aria-labelledby`, GitHub's `CANCELLED`).
- Logic lives in `src/services/` with a `bun:test` suite in `tests/`; components stay
  thin. Tests have no DOM, so components are checked through `renderToStaticMarkup`.
- `noUncheckedIndexedAccess` types every index read as possibly `undefined`. Guard or
  destructure instead of adding `!`. Tests get items through `tests/support/items.ts`:
  `itemAt` (throws on a negative index), `lastItem` and `present`.
- Reach for `src/components/ui/` first. `Button` has variants, sizes and a
  `disabledReason` that explains a disabled button in a tooltip while it stays
  focusable. Menus have `MenuCheckboxItem`, `MenuRadioGroup` and `MenuRadioItem` for
  ticked choices. Also there: `Dialog`, `Select`, `Switch`, `Checkbox`, `Tooltip`,
  `Badge`, `StatusDot`, `Table`, `Empty`, `Skeleton`, `Spinner`, `NumberField` (every
  number input), `MiddleTruncate` (paths and branch names), `Collapsible`, `Popover`
  and `RefreshIcon` (the refresh arrows, turning while busy); `Input` takes
  `font="mono"`. Confirmations use `useConfirmation()`; classes merge with `cn()` from
  `src/lib/utils.ts`.
- Tell the user a save worked with `toast()` (`components/ui/toast.tsx`). Copy
  buttons use `useCopyToClipboard()`, which ticks the button when you pass `inline`
  and toasts otherwise. Failures stay inline beside what failed; one with nowhere on
  screen to go (a copy, a search palette action) is a `kind: 'error'` toast, which
  stays until it's dismissed. Something reversible happens straight away with an
  Undo toast; `useConfirmation()` is for what can't be undone or changes the proxy.
- Never branch on a command's error sentence. A command whose failure the webview acts
  on returns a `CommandError` (`src-tauri/src/command_error.rs`: kind, and the core's
  status and reason when it answered), read with `readCommandError`
  (`src/services/commandError.ts`); management requests and core installs do. Ones
  only shown can stay a string. Other programs' text (ssh's stderr) is still matched.
- Commands go through `invokeCommand` (`src/native/commands.ts`), never `invoke`, and
  each has an entry in its domain's file under `src/native/` that
  `tests/commandParity.test.ts` checks against the Rust signature. Its types are
  generated: `#[derive(TS)]` on the Rust type, listed in `src-tauri/src/bindings.rs`,
  then `bun run bindings`. Don't copy them into TypeScript; where TypeScript wants a
  union and Rust has a `String`, make it a Rust enum. A string Rust only stores,
  passes on from another program (GitHub's words, a transcript's) or shares as words
  with a script on a machine keeps its `String` with `#[ts(type = "...")]` giving the
  values its doc lists. A field serde may skip needs `#[ts(optional)]` (the parity
  test checks); an input whose fields all have defaults takes
  `#[ts(optional_fields)]`. `types.ts` is one namespace, so a nested type with a vague
  or clashing name gets `#[ts(rename = "...")]`; a command's own argument or result
  type keeps its Rust name, since the parity test matches on it, so rename that one in
  Rust. Every registered command is listed, and the parity test fails on a missing
  entry or on an `invoke` import outside `src/native/`.
- Send alerts with `notify()` from `src/services/notify.ts`; it covers the Mac, the
  phone and the alert history. It toasts instead of notifying while the window is in
  front and merges repeats within ten minutes into one entry (never an agent's
  needs-you alerts or a setup change), so leave both to it. An alert's `subject` is what opens it and
  what its repeats are matched by. Name the one thing it's about (a provider for a
  limit's pace), or list them in `machines` or `accounts` when there are several;
  those, and alerts with no subject, are never merged.
- Start every helper process through `configure_helper_command` (tokio: ssh, sh, git,
  ping) or `configure_background_command` (std: the core, the update helper, `open`,
  anything that can outlive the moment), so it gets none of Arbor's open files; on
  macOS a child otherwise inherits every file not marked close-on-exec. Open links
  and files with `system_open::open_with_system`, never `app.opener().open_url` or
  `open_path`, which leave a zombie `open` behind until Arbor quits.
- config.yaml owns the core's settings. config.toml keeps Arbor's own, the plaintext
  management key, client key names by fingerprint and paused keys, and nothing else
  (`core_config/ownership.rs`); never copy a core setting into it. A start only adds
  the management key and a missing port to an existing config.yaml; saves write the
  yaml and read it back into memory. Every write to config.yaml, alias edits included,
  patches the file under `lock_core_config_file`, never through the core's config
  API, and puts a setting only at its v8 path, taking out the old spelling in the
  same edit.
- Settings hold configuration. Main pages stay compact. Each `SettingsRow` or
  `SettingsSection` takes a `settingId` listed in `src/services/settingsIndex.ts`,
  which feeds Settings search and ⌘K; a test fails when a row and the index disagree.
- Comments say why something is done.

## Hard rules

- The real app and its live data are off limits: don't launch it, and don't read or
  change the real config, credentials or usage database. Work in the mock and tests.
- Claim, reset and redeem calls (quota resets, reset credits, banked resets) are
  only ever mocked. A real call uses something up for good.
- Tests don't SSH anywhere real and don't touch the network. On the TypeScript side,
  `mockCommands` from `src/dev/mock/answers.ts` stands in for Tauri, never `mockIPC`
  itself (the parity test checks), so a test's answers are typed like the mock's; Rust
  tests work from sample command output.
- Secrets (account tokens, MCP server env and headers, env values in agent settings)
  are never displayed, logged or saved in the webview, `localStorage` included. Setup
  scans send the UI names and salted fingerprints only.
- Data from agent transcripts and other apps' databases is linked by the ids they
  store, not by heuristics, and limited to the fields a feature uses. Conversation
  text (prompts, replies, summaries, tool inputs and outputs) is never read or kept,
  except by the session archive.
- The archive's exception has hard edges. Raw bytes live only in a store's `chunks/`
  and, for a file still growing, `pending/`. `archive.db`, `journal/`, listings, logs
  and every archive command hold ids, paths, sizes, hashes and times, and the token
  count keeps a hash of each call's id with its day, model name and token numbers.
  Claude Code's own totals keep each machine's days with model names, token and session
  counts. Nothing more. Every new archive command gets a SECRET test.
- Nothing in `chunks/` is ever deleted or rewritten, apart from swapping a
  proven-corrupt file for a verified copy with the same hash.
- Archive tests stay away from `/Volumes/Archive`, the app's `session-archive/` and real
  homes. They use temp stores and temp HOMEs, and the lister runs under `sh` and
  `dash`.

## Shipping a release

Releases are the maintainer's job, or yours only when the maintainer has said to release.

1. `git fetch origin`, rebase onto `origin/main`, and pick the next patch version
   that no one has taken, counting up from `src-tauri/Cargo.toml` there (the repo's
   `v*` tags belong to upstream). Someone else may be releasing too.
2. Run `ARBOR_RELEASE_SUMMARY="…" ./scripts/publish-local-update.sh <X.Y.Z>`: the
   summary is required, one feature-level line (see the notes rules below), and
   `ARBOR_RELEASE_CHANGES` can add up to three high-level changes, one a line. It
   won't start with uncommitted changes or off `origin/main`, and it claims the
   number in the feed before anything else (`.claims/X.Y.Z` there), so it refuses a
   number another run is publishing or has published. A worktree with no `.env` gets
   a link to the main checkout's, where the keys a release needs are. It prints the notes,
   runs `bun run verify` and `bun run verify:rust` (see Running things), writes the
   version into `src-tauri/Cargo.toml` and `src-tauri/Cargo.lock`, builds and signs the
   app, and puts the DMG and a manifest (notes included) in
   `~/Library/Application Support/Arbor Updates` (the loopback feed there only
   serves older apps). Then it prints what to run next.
3. Commit just the Cargo files and the notes using the message file it wrote:
   `git commit -F <file> -- src-tauri/Cargo.toml src-tauri/Cargo.lock release-notes.json`.
   That gives the subject `Release Arbor X.Y.Z` with the summary as the body.
4. `git fetch origin` once more. If `origin/main` moved while you built, the number
   may be taken: rebase and publish the next one.
5. Push to `main` on `origin`.
6. Run `./scripts/publish-github-release.sh <X.Y.Z>`. It checks the feed's DMG is the
   one this release built, then creates the `arbor-vX.Y.Z` release on
   `aaronvanston/arbor` with the notes, the DMG and the signed update list
   `arbor-update-darwin.json` attached (`--dry-run` to look first). Apps update from
   the newest GitHub release, so none is offered this one until it runs. Signing needs
   the "Arbor release signing key" in the release Mac's Keychain.

Versions are only ever changed by the script, and tags only by the GitHub script:
`arbor-vX.Y.Z`, never `v*`, which are upstream's and would set off upstream's release
workflow. Never `git push --tags`.

Release notes are public and kept in `release-notes.json`: a short summary of what the
release adds or changes at a feature level ("Sync: keep rules and commands per
machine."), plus at most three high-level changes. Never commit subjects, screen paths,
internals, usage figures, other apps' names, machines, people, emails or paths;
`release-notes.mjs` refuses notes naming them. `ARBOR_RELEASE_SUMMARY="…" node scripts/release-notes.mjs preview --pending <X.Y.Z>`
checks the next release's notes, and `node scripts/release-notes.mjs check` checks them all.

## Git habits

- Base work on `origin/main` (github.com/aaronvanston/arbor). EasyCLIProxyAPI, if
  you add it as `upstream`, is never a base for new work.
- One logical change per commit, with an imperative, plain-English subject about what
  the user gets and a short body on why.
- No bare `git stash`: every worktree shares the stash. Use a WIP commit, or a named
  `git stash push -m <unique>` applied by SHA.
- Push only when releasing or asked to.
